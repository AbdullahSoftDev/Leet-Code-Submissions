# Jump Game II

## Problem Summary

Given a 0-indexed integer array `nums` where `nums[i]` represents the maximum jump length from index `i`, starting at index 0, return the minimum number of jumps required to reach the last index. It's guaranteed that reaching the last index is always possible.

**Example:**
```
Input: nums = [2,3,1,1,4]
Output: 2
Explanation: Jump 1 step from index 0 to 1, then 3 steps to the last index.
```

## Why the Naive Approach Fails

A brute-force solution would try every possible jump from the current index, recursing into each, and take the minimum jump count across all valid paths. This is correct but exponential — in the worst case it explores every combination of jump choices, giving roughly O(2^n) or worse depending on the jump range values. For large arrays this is far too slow.

A better naive approach is dynamic programming: `dp[i]` = minimum jumps to reach index `i`, computed by looking at every index that could jump to `i`. This works but costs O(n²) time, since for every index you may scan back through many previous indices.

## The Greedy / BFS-Style Insight

The breakthrough is realizing you don't need to know exactly *which* index you jumped from — you only need to know the **farthest index reachable** at each jump count. This is conceptually identical to BFS on an implicit graph where each "level" is a jump:

- Level 0 (0 jumps): only index 0 is reachable.
- Level 1 (1 jump): every index from 1 up to `nums[0]` is reachable.
- Level 2 (2 jumps): every index reachable from *any* index in level 1's range.
- ...and so on.

Since farther reach is never worse than shorter reach (more options, never fewer), we don't need to track the entire range explicitly — just its farthest edge.

## Algorithm Walkthrough

Maintain three variables while scanning the array once:

| Variable | Meaning |
|---|---|
| `jumps` | number of jumps used so far |
| `current_end` | the farthest index reachable using `jumps` jumps (edge of current frontier) |
| `farthest` | the farthest index reachable using `jumps + 1` jumps, updated continuously |

For each index `i` from `0` to `n-2`:
1. Update `farthest = max(farthest, i + nums[i])` — this always happens, regardless of anything else.
2. If `i == current_end`, it means the scan has now covered every index inside the current frontier — there's nothing left to check without committing to another jump. So: increment `jumps`, and set `current_end = farthest`.

The loop stops at `n - 2` rather than `n - 1` because landing exactly on the last index shouldn't itself trigger a "phantom" extra jump — you've already arrived, no further jump is needed to be *at* the destination.

## Manual Trace Example

`nums = [2,3,1,1,4]`

| i | nums[i] | farthest | i == current_end? | jumps after | current_end after |
|---|---|---|---|---|---|
| 0 | 2 | max(0, 0+2)=2 | yes (0==0) | 1 | 2 |
| 1 | 3 | max(2, 1+3)=4 | no (1≠2) | 1 | 2 |
| 2 | 1 | max(4, 2+1)=4 | yes (2==2) | 2 | 4 |
| 3 | 1 | max(4, 3+1)=4 | no (3≠4) | 2 | 4 |

Loop ends (range stopped at i=3, since n-2=3). Result: **2 jumps.**

## Why the Greedy Choice Is Always Optimal

At any point, all indices within the current frontier are reachable with the same number of jumps. Since the goal is purely to minimize jump *count* (not which specific indices are visited), there's never a reason to prefer a shorter reach over a longer one — a longer reach can only unlock equal or better future options. This greedy "always take the farthest possible frontier" choice can never be suboptimal, which is what makes the linear scan correct without needing to backtrack or compare alternate paths.

## Complexity Analysis

**Time Complexity: O(n)**
The array is scanned exactly once; each index is processed in constant time.

**Space Complexity: O(1)**
Only three scalar variables are used, independent of the input size — no auxiliary arrays or recursion stack.

## Common Pitfalls

- **Confusing `i` (the scanner) with `farthest` (a reachability calculation).** `i` always walks forward one step at a time — it never "jumps to" `farthest`. Understanding this distinction is essential; conflating them is the most frequent source of bugs when first implementing this pattern.
- **Comparing `i` against the value just computed in the same iteration**, instead of the `current_end` carried over from the previous jump trigger. The check must always use last iteration's committed boundary, not the number just calculated this round.
- **Looping through `n - 1` instead of `n - 2`.** Since you don't need a jump *to arrive* at the destination, looping one index further than necessary can cause an off-by-one overcount in edge cases.
