# Jump Game

A solution to the classic **Jump Game** problem (LeetCode #55), solved using a **greedy, single-pass** approach in O(n) time and O(1) space.

---

## 📋 Problem Statement

You are given an integer array `nums`. You are initially positioned at the array's **first index**, and each element in the array represents your **maximum jump length** at that position.

Return `true` if you can reach the last index, or `false` otherwise.

### Examples

**Example 1:**
```
Input:  nums = [2,3,1,1,4]
Output: true
Explanation: Jump 1 step from index 0 to 1, then 3 steps to the last index.
```

**Example 2:**
```
Input:  nums = [3,2,1,0,4]
Output: false
Explanation: You will always arrive at index 3 no matter what.
             Its maximum jump length is 0, which makes it impossible
             to reach the last index.
```

### Constraints

- `1 <= nums.length <= 10^4`
- `0 <= nums[i] <= 10^5`

---

## 💡 Approach

### Why not brute force?

The naive approach — trying every possible sequence of jumps from every index — works but is exponential in the worst case, since the same sub-problems get recomputed repeatedly along different paths.

### The greedy insight

Instead of asking *"which exact path reaches the end?"*, we ask a simpler question while scanning left to right:

> **"What is the farthest index reachable using everything I've seen so far?"**

We track this as a single variable, `max_reach`. As we walk through the array:

1. **Check reachability** — before processing index `i`, confirm `i <= max_reach`. If not, the "wave" of reachability has stalled and can never restart — return `False`.
2. **Extend the reach** — if `i` is reachable, update `max_reach = max(max_reach, i + nums[i])`.
3. **Early exit** — if `max_reach` ever reaches or exceeds the last index, return `True` immediately.

### Why greedy works (correctness intuition)

`max_reach` represents the **union of every reachable position** using any combination of jumps made so far — not one committed path. Because it only ever grows (or stays the same) as we scan forward, once it stalls at some index `i` (i.e., `i > max_reach`), there is no way to "reach back" and pick a better combination of earlier jumps. The wave has permanently stopped, so the array is unreachable beyond that point.

This is what makes a single greedy pass provably correct here, without needing dynamic programming or backtracking.

## 🧮 Complexity

| Metric | Complexity | Explanation |
|---|---|---|
| Time  | `O(n)` | Single left-to-right pass over the array |
| Space | `O(1)` | Only one variable (`max_reach`) is maintained |

---

## 🖥️ Solution

```python
class Solution(object):
    def canJump(self, nums):
        """
        :type nums: List[int]
        :rtype: bool
        """
        max_reach = 0
        last_index = len(nums) - 1

        for i in range(len(nums)):
            if i > max_reach:
                return False

            max_reach = max(max_reach, i + nums[i])

            if max_reach >= last_index:
                return True

        return True
```

### Notes on this implementation

- The stuck condition is `i > max_reach` — index `i` is unreachable given everything computed so far.
- The `max_reach` update only happens once we've confirmed `i` is reachable.
- The trailing `return True` handles the edge case where the loop finishes naturally (e.g., a single-element array) without either the early-exit or the stuck condition firing.

---

## 🔍 Trace Through the Examples

### `[2,3,1,1,4]` → `True`

| i | i <= max_reach? | nums[i] | max_reach after update | max_reach >= last_index (4)? |
|---|---|---|---|---|
| 0 | 0 <= 0 ✅ | 2 | max(0, 0+2) = 2 | No |
| 1 | 1 <= 2 ✅ | 3 | max(2, 1+3) = 4 | **Yes → return True** |

### `[3,2,1,0,4]` → `False`

| i | i <= max_reach? | nums[i] | max_reach after update | max_reach >= last_index (4)? |
|---|---|---|---|---|
| 0 | 0 <= 0 ✅ | 3 | max(0, 0+3) = 3 | No |
| 1 | 1 <= 3 ✅ | 2 | max(3, 1+2) = 3 | No |
| 2 | 2 <= 3 ✅ | 1 | max(3, 2+1) = 3 | No |
| 3 | 3 <= 3 ✅ | 0 | max(3, 3+0) = 3 | No |
| 4 | 4 <= 3 ❌ | — | — | **Stuck → return False** |

---

## ⚠️ Edge Cases Worth Considering

- **Single-element array** (`[5]` or `[0]`): the start is already the last index, so the answer should be `True`. The loop body never triggers `False` or the early-exit `True`, so the trailing `return True` is essential here.
- **All zeros beyond the first element** (`[1,0,0,0]`): the wave stalls quickly; confirms the stuck-detection logic works even without ever getting close to the end.
- **A single large jump at the start** (`[100,0,0,0,0]`): `max_reach` jumps far past `last_index` on the very first iteration, so the early exit should fire immediately.
- **Zero at index 0 with array length > 1** (`[0,1]`): `max_reach` stays at 0, and at `i=1`, `1 > 0` → correctly stuck, returns `False`.

---

## ▶️ Usage

```python
obj = Solution()
print(obj.canJump([2, 3, 1, 1, 4]))   # True
print(obj.canJump([3, 2, 1, 0, 4]))   # False
```
